# Legacy pipelines shutdown

The production `docker_pipelines` command replaces its shell with the Go process. SIGINT and SIGTERM stop the HTTP listener and wait for active requests to finish before returning from the service. Active request contexts stay live so token-disbursement or referral operations can finish their existing transaction and receipt work. No new work is accepted during the drain.

There is no forced drain deadline in the application: a long operation can delay exit. The maintenance caller must allow it to finish and verify the actual container exit; a short Docker stop timeout can still force termination externally. The backend container also now replaces its shell, exposing the backend's existing signal/shutdown handling without changing its current ten-second drain policy.

Run `go test ./pipelines/server` for real loopback drain coverage and Unix process tests that execute both actual Docker command strings (with a local fixture binary), verify PID preservation and argument expansion, deliver SIGINT/SIGTERM during a blocked request, and require its response to complete before process exit. These fixtures perform no database, Ethereum or notification calls.

Database credentials are read through the existing `MYSQL_APP_PASSWORD`/`DB_PASSWORD` fallback; provider endpoint and signing key are resolved from `ETH_NETWORK_URL`/`KITN_PRIVATE_KEY` when their legacy CLI flags are empty. Explicit CLI settings remain supported, but the container commands no longer expand those secrets into arguments or flag defaults. Public port/host/contract/table arguments retain their previous behavior.

For the old deployed pipelines binary, a direct signal is not a drain: it has no shutdown listener. Before its one-time replacement, bind its container/image/process generation and source, hold verified caller/admission paths, and establish completion of any existing request before stopping it. Current source includes Cloud Scheduler jobs `referral-redeem-prod` and `tokens-disburse-prod`; these are deployment templates, so inspect actual current jobs and routes rather than assuming their schedules. A proxy introduced now cannot account for a handler that started earlier or continues after its client disconnected. Zero TCP/DB activity or elapsed time alone does not prove completion. The disbursement path polls on-chain events without a deadline and then performs synchronous database updates; an observed handler completion establishes that those calls returned, while correctness of individual financial receipts is a separate check. No automatic transaction replay is part of this change.
