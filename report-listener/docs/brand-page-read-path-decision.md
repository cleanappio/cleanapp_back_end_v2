# Brand page read path: decision memo (first deliverable, 2026-10-17)

Worktree `work/cleanapp-claude-cohort-cache`, branch `claude/brand-cohort-cache`, base `7d3cc18c` (draft PR 174 head; not rebased on the PR 183 merge, which only touched email-service). Nothing committed, nothing touched in production.

Labels: **MEASURED** = production measurements already on file (not re-run). **ESTIMATE** = arithmetic from those. **LOCAL** = run on this machine (no MySQL/Docker here; MySQL fixtures are CI-only). **CRITIC** = conclusion of one of three independent refutation passes run over this design and the code.

## 1. Chosen approach, why, and what it costs

**Cost model that fits every measured component (MEASURED → ESTIMATE).** Google's cohort is 61,184 rows; the PR 174 base query spends 0.42 s on the covering brand-index scan and then ~1 s per lookup table (metadata 1.15, raw 0.48, evidence 1.0 for only 31 matching rows, source projection 1.7, owners 0.9, status 0.25) regardless of row width. That is *pages touched × ~1 ms random read* under a buffer pool that background jobs cycle every few seconds. Any design that still does O(cohort) seq-keyed lookups per request stays at 5–7 s cold; that is why narrow SQL, hints, hash joins and SQL-side counts all failed.

**Design C′ (chosen): cache the guard-free cohort; evaluate every publication guard live, over the whole cohort, before grouping.**
1. Split PR 174's reader into `loadProjectedEvidenceCohort` (full-cohort read: base query + dirty-source fallback + case references in one RO/REPEATABLE READ tx, stamped with a snapshot time) and `finishProjectedEvidencePage` (pure Go grouping for kind/sort/offset + the existing bounded hydration). *Done in the patch.*
2. The cached cohort holds only slowly-changing, non-guard data per seq: preferred-analysis tuple, evidence kind/version/relationship/presence bits, source-projection fields, case refs. It must **not** hold the four publication guards (`public_id<>''` under `COLLATE utf8mb4_bin`, `PublicVisibilityWhereSQL` = not quarantine/shadow, no inactive `report_status`, private-owner `COUNT(*)=0`) nor `privacy_restricted`. *Patch still caches the guarded cohort → must change.*
3. Per request, inside the 8 s RO/RR tx: run **one** live guard query over the full cached id list (plus a live membership re-scan of `report_analysis` via `idx_ra_brand_valid_class_core` so an invalidated/re-attributed analysis drops out), returning the passing seqs and live `privacy_restricted`; build the record slice from the passing subset; then the existing pure grouping (counts, `KindCounts`, overview, family representatives, first-eight-then-privacy samples) and bounded hydration. Guards are never cached, so counts and privacy are live by construction and the existing oracle fixtures apply unchanged.
4. Cache: process-local, opt-in env (default off → rollback = unset + redeploy; no schema, no triggers), single-flight refresh per (brands, language) with its own bounded budget (default 60 s), demand-driven (refresh only keys that were requested), bounded key count, LRU eviction. On a miss the request falls through to today's direct path and schedules a refresh. *Done in the patch except the key bound/eviction and the demand-only rule.*

**Why not C as I first specified it (snapshot counts + re-guard of displayed rows only).** CRITIC (contracts): refuted. `evidence_projected_publication_mysql_test.go:80-89` ("Cache warmth cannot freeze live publication") requires `Overview.TotalReports` and `KindCounts` to drop from 9 to 8 in the very next request after a private-owner insert or a `resolved` status, and to come back when reverted; snapshot counts cannot satisfy that at any refresh interval. It also omitted `privacy_restricted` (a report redacted after the snapshot would leak URL/excerpt/sample title for up to the interval), dropped whole families instead of promoting the next visible member, and could never un-block a report that the snapshot had filtered out. The patch below implements that refuted variant and must be reworked.

**Cost (ESTIMATE, Google, cold pool).** Per request: live guards over 61k seqs ≈ 2.8 s if done as per-seq lookups (raw 0.48 + owners 0.9 + status 0.25 + metadata 1.15, MEASURED components) + membership re-scan 0.42 + Go grouping 0.05–0.15 + bounded hydration 0.3–0.5 ⇒ **≈ 3.6–3.9 s**, ~2× headroom under 8 s, vs. >8 s today. Treating `public_id` as cohort data rather than a guard removes 1.15 s (judgment call; the publication fixture mutates owners, status and visibility, not `public_id`). A cheaper guard evaluation — scanning the small *blocking* sets (inactive statuses, private owners, non-public visibility) once via their covering indexes and applying them as set differences in Go — is cohort-size-independent and could bring guards to well under 1 s, but full scans measured 7–14 µs/row here, so it depends on blocklist sizes nobody has measured. Per write: zero (no triggers). Background: one cohort read per requested large brand × language per interval, 6.6 s+ DB time each (MEASURED base query; fallback/cases unknown). Memory: ~40 MB per 61k-record cohort (ESTIMATE from `evidenceRecord` layout) in a listener at ~60 MB RSS.

**Alternatives (ranked by the three critics).**
- **A′ — trigger-maintained, brand-clustered per-(brand, seq) publication projection.** Best steady-state physics (one contiguous ~7 MB scan, ESTIMATE 50–150 ms cold) and exact + live only if its triggers cover `reports_owners`, `report_status`, `report_raw.visibility` and wire privacy JSON too. ~15 triggers across 6–7 tables, membership from the PK-less `report_analysis`, chained through two existing projections, plus backfill/`Verify`/repair: highest correctness risk, multi-day. The right end state; not the first step.
- **B — covering secondary indexes + column narrowing.** No derived data, satisfies every contract trivially, but only ~1.5–2× on 2–3 of six structures ⇒ Google ≈ 4.5 s (ESTIMATE) with no headroom, and needs online DDL on production. Rejected as the primary fix; could be a complement to C′ for the guard tables.
- **D — read replica / off-primary.** Forbidden by the 2026-10-17 08:00 UTC billing cutoff; would also not fix cold per-row cost, only isolate it.

**Operational facts (CRITIC, operations; verified in `platform_blueprint/deploy/prod/docker-compose.yml`).** Exactly one `cleanapp_report_listener` container, replaced on every deploy ⇒ process-local cache is adequate but cold after each deploy, so the first Microsoft/Google request after a deploy behaves as today unless a warm list is set. Timer-driven refresh of every brand × language is new permanent load on a saturated host; refresh must be demand-driven and single-flight. The handler must report the snapshot time (`as_of`) when served from the cache. A 60 s *background* budget is not a request-timeout change, but it is a new serialized background consumer and should be stated as such in the release note.

## 2. The patch (reworked to C″, committed on `claude/brand-cohort-cache`)

**Superseded variant.** The first patch implemented design C as first specified (snapshot counts + live re-guard of the displayed rows only). CRITIC (contracts) refuted it with `evidence_projected_publication_mysql_test.go:80-89` ("Cache warmth cannot freeze live publication"), and the 06:27 UTC measurement (`claude-live-guard-google-explain-analyze-20261017T0627Z.{json,txt}`) killed its successor C′ (one live per-seq guard over the full cohort: timed out at 8 s with 54 % of Google processed). The 06:31 UTC blocking-set sizes (`claude-blocking-set-sizes-20261017T0631Z.{json,txt}`) made C″ buildable. The patch now implements C″ exactly as section 6 specifies.

**What changed, by file.**
- `report-listener/database/evidence_projected.go` — one query builder, `projectedEvidenceQuery(f, budget, livePublicationGuards)`. `projectedEvidenceBaseQuery` (direct path) is byte-identical to the base commit's statement (checked with a throwaway equality test against the `7d3cc18c` builder; the sqlmock order test `TestPublicEvidenceProjectedCleanScopeGroupsAndHydratesExactNullableSelection` still passes, so the cache-off path issues the same queries in the same order). `projectedEvidenceCohortQuery(f, budget)` is the refresh variant: same membership (`brand_name IN … AND classification='digital' AND is_valid`), same non-empty `public_id COLLATE utf8mb4_bin` identity, same analysis/evidence/source stream, minus `PublicVisibilityWhereSQL`, the `report_status NOT EXISTS`, the owner `COUNT(*)=0` and the `report_raw` join only they used; it still selects `COALESCE(p.privacy_restricted,FALSE)` but nothing relies on it (overwritten live). `finishProjectedEvidencePage`/`hydrateProjectedEvidencePage` take the live record slice; `hydrateProjectedEvidenceOutput` keeps its fail-closed generation check for the direct path and accepts a projection invalidated after the snapshot on the cached path (its columns are the last complete normalizer output: bounded staleness, not a 500).

## 3. One bounded measurement to approve

One read-only statement on the primary, once, in a `READ ONLY, REPEATABLE READ` transaction with `MAX_EXECUTION_TIME(8000)`, at a normal-churn moment, from the listener's existing runtime connection (same pattern as the `candidate-*-profile` harnesses): **the live full-cohort guard for Google** —
`SELECT COUNT(*), SUM(COALESCE(p.privacy_restricted,FALSE)) FROM (SELECT DISTINCT ra.seq FROM report_analysis ra FORCE INDEX (idx_ra_brand_valid_class_core) WHERE ra.brand_name IN (<google scope>) AND ra.classification='digital' AND ra.is_valid=TRUE) c LEFT JOIN report_metadata_projection m ON m.seq=c.seq LEFT JOIN reports fallback ON fallback.seq=CASE WHEN m.seq IS NULL THEN c.seq END LEFT JOIN report_raw rr ON rr.report_seq=c.seq LEFT JOIN report_evidence_source_projection p ON p.seq=c.seq WHERE (CASE WHEN m.seq IS NOT NULL THEN m.public_id ELSE fallback.public_id END COLLATE utf8mb4_bin)<>'' AND (rr.visibility IS NULL OR rr.visibility='public') AND NOT EXISTS (SELECT 1 FROM report_status rs WHERE rs.seq=c.seq AND rs.status IS NOT NULL AND rs.status<>'active') AND (SELECT COUNT(*) FROM reports_owners ro WHERE ro.seq=c.seq AND ro.owner IS NOT NULL AND ro.owner<>'' AND ro.is_public=FALSE)=0`
run as `EXPLAIN ANALYZE`, recording wall time per join and `Innodb_buffer_pool_reads` delta. **Decision rule:** ≤ 4 s ⇒ C′ is viable (request ≈ guard + ~1 s); > 5 s ⇒ C′ is dead and A′ (trigger projection) is the only exact-and-live path. Second, if approved later: the uncapped cohort read for Google (60 s budget) to set the refresh cadence; and four covering-index `COUNT(*)`s of the blocking sets to decide lookups vs set-difference guards.

### Result (MEASURED, 2026-10-17 06:27 UTC, one execution, approved by Boris)

Evidence: `claude-live-guard-google-explain-analyze-20261017T0627Z.{json,txt}`. **The guard timed out at the 8 s cap** with 33,197 of 61,046 distinct Google seqs processed at 7.9 s (~54 %) ⇒ **≈ 11–14 s cold for the full cohort (ESTIMATE). C′ with per-seq guard lookups is dead.** Components: covering brand scan 61,190 rows 1.03 s; DISTINCT + materialize 1.33 s; owner guard 49 µs/seq (≈ 3.0 s full); metadata PK 44 µs/seq (≈ 2.7 s); source-projection PK 45 µs/seq (≈ 2.8 s); report_raw PK 15 µs/seq (≈ 0.9 s; no row exists for any Google seq); **report_status anti-join: 1,606 inactive rows materialised once in 33 ms, then ~10 µs per probe (≈ 0.6 s)**. Per-lookup latencies were ~3× worse than the 21:12 UTC measurement, so the cost is load-dependent. Global `Innodb_buffer_pool_reads` delta over the 8 s: 24,808 pages (~388 MB, includes other sessions); no disk temp tables.

**What this changes.** The one live guard the optimizer could materialise (status) cost 33 ms + hash probes; every per-seq lookup costs ~3 s per table at this load. So the viable exact-and-live paths are now: **A′** (trigger-maintained brand-clustered projection carrying the guard flags; one contiguous scan per request), or **C″** = cached guard-free cohort + guards evaluated as *materialised blocking sets* (inactive statuses, private owners, non-public `report_raw`, `privacy_restricted`, empty `public_id`) probed by hash — cost proportional to the blocklist sizes, which are unmeasured. The base query deliberately avoided materialising private owners (PR 174 doc: "instead of materializing unrelated private owners"), so the private-owner set may be large; `privacy_restricted` and `public_id` have no index, so their blocklists would need either a tiny online index or bounded-staleness treatment. **Next bounded measurement (not yet approved):** `EXPLAIN` (no execution) plus capped `COUNT(*)` of each blocking set to size them; if private owners + non-public raw are ≲ 100k rows, C″ is buildable without triggers; otherwise A′.

## 6. Revised decision after the two approved measurements (06:27 and 06:31 UTC)

**Blocking-set sizes (MEASURED, `claude-blocking-set-sizes-20261017T0631Z.{json,txt}`):** private owners (`is_public=FALSE AND owner<>''`) **0** rows of 526,916; non-public `report_raw` **1,480** (`shadow`) of 163,651; inactive `report_status` **1,606** (the whole table); `privacy_restricted` **0** of 114,663 source-projection rows (448 dirty); empty/NULL `public_id` **0** of 137,727 metadata-projection rows. Costs: owners 7 ms (indexed range), shadow via covering index scan 1.1 s for the full GROUP BY (a `visibility<>'public'` range would touch ~1.5k entries), the two unindexed full scans 1.9 s each (~17 µs/row).

**Conclusion: C″ is viable without triggers.** Per request, served from the cached guard-free cohort: three indexed blocking-set reads (status 1.6k, shadow 1.5k, private owners 0 → ESTIMATE 20–100 ms cold combined) + `privacy_restricted` blocklist (needs a small online index on `report_evidence_source_projection(privacy_restricted)`, 35 MB table, seconds to build; or bounded staleness, explicitly rejected by the contracts critic) → Go set-difference over the 61k cached seqs → existing pure grouping → bounded hydration. **ESTIMATE ≈ 0.4–0.9 s cold, independent of cohort size and of background load**, exact and live for every publication guard. `public_id` becomes cohort data (evaluated at refresh; it is never emptied in practice: 0 empties) unless a `(public_id)` index is added to the metadata projection. Cohort membership (`is_valid`, brand re-attribution) is also refresh-time data — the one bounded-staleness item left; state it in the release note.

**Independent quick win, no cache, no schema (B′):** rewrite the base query's owner guard (`(SELECT COUNT(*) …)=0` with `JOIN_INDEX(ro idx_is_public)`) and the visibility predicate as `NOT EXISTS` anti-joins so the optimizer materialises the (empty/tiny) blocking sets once, as it already does for `report_status` (33 ms). ESTIMATE: removes 1.4–3.9 s from the measured Google base query. PR 174's doc chose the correlated form "instead of materializing unrelated private owners"; the measured set is 0 rows, and even a 300k-row set would cost ~2 s — no worse than today. The existing `ProjectedPublicationBlockerParity` fixture is the parity proof. This alone does **not** get Google under 8 s under load (metadata + evidence + source lookups remain 3.9–6.5 s), but it lowers refresh cost for C″ and helps every brand.

**Rework of the uncommitted patch (precise):** keep the cohort split, budget parameterisation, single-flight cache and sqlmock scaffolding; drop the four guards and `privacy_restricted` from the refresh query; add `loadPublicationBlocklists(ctx, tx)` returning three (four with the index) seq sets via the covering indexes; apply them in Go before `groupEvidenceRecords`, overwriting `PrivacyRestricted`; remove snapshot-count semantics; bound keys; fix the fixture seq range and assertions and run every existing projected parity sub-fixture through the cached path. Measurement to validate C″ when funded again: one `EXPLAIN ANALYZE` of the three blocklist reads plus the bounded hydration for Google page 1 (≤ ~1 s expected).
